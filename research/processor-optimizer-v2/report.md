## 0. 結論（先に）

| 問い | 答え（根拠） |
|---|---|
| 1. なぜ 250 MB が 250 MB のままか | 現行の最適化（`runners.ts:216`）は **pdf-lib で再保存するだけで、画像には一切触れない**。再保存で減るのは 1,359 bytes（261,547,235 → 261,545,876）。「1 バイトでも小さければ再保存版を返す」ルールなので、約 250 MB の再保存版が返る（§8） |
| 2. なぜ 512 MiB は拒否、1 GiB は通るか | 見積りピーク = `3.5 × 元ファイル + 256 KiB`（`budget.ts:222-232`）。これを実行直前に `canStartNextFile`（`PdfTools.tsx:285`）がメモリ上限と比較する。261.5 MB では 873.3 MiB → 512 MiB 拒否、1 GiB 実行（§4） |
| 3. Acrobat は何をしたか | **未解決**（実ファイル未提供）。ただし同等の合成ファイルは**可逆だけで 0.36 MB** になるので、2 MB は非可逆を必要としない。ローカル解析ツールを用意した（§11） |
| 4. 可逆でどこまで減るか | 旧 Comparator 型の A1 × 5 p で **261,547,235 → 355,046〜376,869 bytes（99.86 %）**、デコード後の画素は全件一致。5 MB 未満・25 MB 未満はいずれも可逆で達成（§9, §12） |
| 5. ベクター・テキストを画像化せずに縮められるか | できる。画像 XObject のストリームだけを書き換え、それ以外のオブジェクトはそのまま。テキスト、ベクター、注釈、リンク、フォーム値、メタデータ、回転、CropBox、共有画像、SMask を独立に検証し、全件一致（§15） |
| 6. 250 MB を 512 MiB で安全に扱えるか | **未証明 → Stage 1 では DEFERRED**。約 250 MiB の入力は **Stage 1 では 1 GiB プリセットが必要**。方式 R（固定分を事前判定 + 圧縮次第の部分を実行時の実バイトで管理）は推奨する構成として残すが、「250 MiB を 512 MiB で」は証明できていない。pako 2.1.0 で見積ると、元を手放しても読み込みの瞬間の余裕は 12.8 MiB しかなく、オブジェクトの負担は合成コーパスでしか測っておらず、ブラウザのヒープ / GC / Blob は未計測（§13） |
| 7. どの画像なら安全に書き換えられるか | Flate、非圧縮、ASCIIHex の連鎖は、どの色空間でもサンプルを保ったまま再圧縮できる（R1）。8 bit の DeviceRGB / DeviceGray / ICCBased(N=3) は、正確に表せる場合に Indexed / Gray / ビット深度の削減もできる（R2）。ただし **`/Interpolate true` の画像は R1 のみ**。DCT / JPX / JBIG2 / CCITT / LZW などは触らない（§6） |
| 8. どの構成にするか | **Hybrid**: pdf-lib（既存）で読み込み、自前の画像書き換え器、pako 2.1.0（既存の直接依存）を **`Deflate` + `onData` のストリーミング**で使って圧縮、自前のチャンク writer（Comparator v2 の考え方を流用）で書き出す（§18-20） |
| 8b. Stage 1 の範囲 | **1 ファイルのみ**。Optimizer v2 で 2 ファイル以上を選んだ場合は明示的に拒否する（先頭だけ黙って処理しない）。他の Processor ツールのバッチ動作は変えない。バッチ / ZIP の Optimizer v2 は DEFERRED（§13b） |
| 9. モード | 既定は**無損失（構造＋画像）**。**軽量（画質が変わります）**はスキャン・写真向けの明示的な選択肢。解像度の削減は別の明示的な選択肢で、既定にはしない（§23） |
| 10. 安全ゲート | 事前判定（入力、読み込み、最大画像の処理、予約枠）と実行時ゲート（実バイト、保持量、出力上限、部分公開なし）。置き換えは元より小さい場合だけ（§14） |

## 3. 現行の Optimize のコード追跡
- UI（`PdfTools.tsx`）
  - `file.arrayBuffer()` → `Uint8Array`（:219）→ `readSourceFacts` → `planOperation`。全ファイルの `bytes` を `planned[]` に保持したまま、1 ファイルずつ処理する。
  - `canStartNextFile(results, plan.filePeakBytes, ceilings)`（:285）: 保持中の出力 + そのファイルのピーク見積り ≤ メモリ上限。
  - `runOptimizeLossless(bytes, token)`（:341）、`checkActualOutput`（:351、≤ 256 MiB）、出力 > 見積りなら拒否（:374-391）。
  - 1 ファイルの公開は `new Blob([bytes.slice().buffer])`（:444-451、もう 1 つコピー）→ `saveAs`。複数ファイルは JSZip（`batch.ts:300-348`）。

- 拒否（`planner.ts:120-143`）: 暗号化、読めない、ページ不正、フォームが読めない / 適用済み署名 → `SIGNATURE_UNSAFE`。XFA は optimize では拒否しない。

## 4. 512 MiB / 1 GiB の再現と算術
本番の関数そのもの（`preservingFileCost` → `canStartNextFile` → `defaultCeilings`）で計算した（`model.json` の `current`）。

| 元ファイル | 出力見積り（1.5S + 256 KiB） | ピーク見積り（2S + 出力） | 512 MiB | 1 GiB | 2 GiB |
|---|---:|---:|---|---|---|
| 250,000,000 B（報告の約 250 MB） | 357.9 MiB | **834.7 MiB** | 拒否 | 実行 | 実行 |
| 261,547,235 B（f01） | 374.4 MiB | **873.3 MiB** | 拒否 | 実行 | 実行 |
| 261,549,245 B（PR #28 で実測した旧 Comparator の出力） | 374.4 MiB | 873.3 MiB | 拒否 | 実行 | 実行 |

- 拒否文は `canStartNextFile`（`batch.ts:221-237`）の「…このファイルの処理に約 873 MiB が必要で、処理メモリ上限 512 MiB を超えます。」。
- 今日受理される元ファイルの上限は、512 MiB で **146.2 MiB**（153,316,790 B）、1 GiB で 292.5 MiB、2 GiB で 585.1 MiB。
- 1 GiB で実行すると構造だけの再保存になり、1,359 bytes 小さい再保存版（約 250 MB）が返る。`checkActualOutput` は 249.4 MiB ≤ 256 MiB で通る。**「1 GiB で成功しても 250 MB のまま」はこの二つで完全に説明できる。**
- 実測では、本番の Optimize が f01 を処理したときの増分 RSS は g1 +250.3 / g2 +250.0 MiB だった（MeasuredOnly）。見積り 873 MiB は保守的な上限である。

## 6. 画像 XObject の分類（census）と推奨

| 分類 | 例 | 推奨 | 理由 |
|---|---|---|---|
| 非圧縮 / FlateDecode（予測器あり・なし）/ ASCIIHex→Flate の連鎖 | f01, f02, f03, f11 | **REWRITE LOSSLESSLY（R1）** | 連鎖を完全にデコードでき、同じサンプルを Flate + PNG 予測器で書き直せる。ColorSpace / BPC / Decode / Mask / ImageMask / SMask / Interpolate は変更しない |
| DeviceRGB 8 bit、色数 ≤ 256（`/Interpolate true` を除く） | f01 | **R1 + R2 → Indexed 1/2/4/8 bit** | 正確なパレット解析（近似しない）。f01 は各ページ 2〜4 色で、1〜2 bit になった |
| DeviceRGB 8 bit、R = G = B | 描画したグレー図面 | **R2 → DeviceGray** | DeviceRGB のときだけ。ICC 空間ではグレー化しない（プロファイルが変わるため） |
| DeviceGray 8 bit、値が 1/2/4 bit で正確に表せる | 二値の図面 | **R2 → 低ビット深度** | 値 ÷ (255 / (2^bpc − 1)) が整数のときだけ |
| ICCBased(N=3) 8 bit | f11 | **R1 + R2（Indexed のベースに同じ ICC を使う）** | グレー化はしない |
| Indexed | f11 | **R1** | パレットと索引はそのまま |
| /Decode 配列、色キー /Mask、/ImageMask、16 bit、1 bit、DeviceCMYK | f11 | **R1 のみ** | サンプルの意味が他のキーに依存するので、表現は変えない |
| **`/Interpolate true`**（色数・ビット深度が R2 の条件を満たしていても） | f11、**f12** | **R1 のみ** | デコード後のサンプルが一致しても、色空間やビット深度を変えた後の補間描画が一致するとは言えない。f12 は同じ 4 色のサンプルを `/Interpolate true` あり（p1）となし（p2、対照）で持ち、対照では R2 Indexed のほうが小さいことをゲートで確認する |
| SMask（それ自体が DeviceGray 画像） | f09 | **R1 / R2** | 独立した画像オブジェクトとして扱う。親の /SMask 参照はそのまま |
| 共有画像（複数ページ + Form 内） | f08 | **R1 / R2、1 回だけ** | 参照先のオブジェクトを 1 回だけ差し替え（`context.assign`）、全参照に効く |
| DCTDecode | f06 | **LEAVE** | 既に非可逆。再デコード・再エンコードは画質を落とす |
| JPXDecode、JBIG2Decode、CCITTFaxDecode | 未遭遇 | **LEAVE** | 既に効率的。JBIG2 の共有辞書などもある |
| LZW、RunLength、ASCII85、Crypt、未知のフィルタ | — | **LEAVE**（実装範囲次第で R1 に昇格） | デコーダを所有していない |
| 読めない・壊れたストリーム | — | **そのまま残し、書き換えない** | 全体を拒否はせず、その画像だけ触らない |
| 暗号化・適用済み署名 | — | **UNSUPPORTED / 拒否**（現行どおり） | 署名方針は変えない |
| 非可逆（DCT、縮小） | — | **OPTIONAL LOSSY**（明示的に選んだ場合のみ） | 8 bit の DeviceRGB/Gray で、/Decode・色キー・ImageMask なし。SMask 本体は対象外 |

**置き換えるのは、候補が元のストリームより小さい場合だけ。** 見た目が似ているかどうかでは安全性を判断しない。可逆の判定は、検証器によるデコード後のサンプル比較で行う。

## 13. メモリモデル
f01（S = 249.4 MiB、Σストリーム ≈ S、オブジェクト 19）で計算した。

**実測した pdf-lib 1.17.1 の読み込み**
- 全ストリームを `bytes.slice` でコピーする（`PDFObjectParser.ts:239-241`、Reuse Scan）。読み込み直後は **元 + Σストリーム**が同時に生きる。
- ストリーム以外のオブジェクトの負担は 1 個あたり最大 17 KB 程度（フォント入り）。保守的な定数として 20,472 B を使う（MeasuredOnly を 2 倍にした値）。

**v2 の項目（RF-30-01 で推奨経路の pako 2.1.0 に合わせて見積り直した）**
- 前回のモデルは最大画像の圧縮を Comparator の自前 DEFLATE の上限（`ownedDeflateBound` / `ownedDeflateScratchBytes`）で見積っていた。これは推奨経路ではないので使わない。Production の `deflateUpperBound` / `PAKO_STATE_BYTES` も、pdf-lib が固定している **pako 1.0.11** から導いたもので、2.1.0 には流用しない。
- 最大画像の処理（f01、4969 × 3509 RGB）= デコードしたサンプル + R1 の予測器付き本体全体 + 最大の R2 形式 + これまでの最良候補（元より小さい場合だけ保持するので ≤ 元のストリーム）+ 圧縮中の候補 + pako 2.1.0 の状態配列 = **218,245,079 B（208.1 MiB）= 52,308,663 + 52,312,172 + 8,723,374 + 52,308,663 + 52,325,047 + 267,160**（`model.json` の `f01.imageWorkTerms`）。
- **pako 2.1.0 の出力の上限は主張しない**。圧縮中の候補は、`onData` で出力バイトを数え、勝てなくなった時点（最良候補または元のストリームを超えた時点）で止める **実行時の上限**で抑える。したがって ≤ 元のストリーム + 出力チャンク 1 つ（16 KiB）。これは Production 段階で実装・試験すべき**設計上の契約**で、pako の性質ではない。
- pako 2.1.0 の状態配列は、ソース（`lib/zlib/deflate.js:1501-1507, 1512, 1553-1554, 1296-1321`、level 9 / windowBits 15 / memLevel 8）から数えた 267,160 B。
- 置き換えたストリーム（元より小さい場合だけ保持）。出力: チャンク writer はストリームをビューとして参照するので、ファイル全体の複製を作らない。Blob への複製 1 回（プラットフォームの前提）。

**pako 2.1.0: 一発呼び出しとストリーミング**（`model.json` の `pakoProbe`、f01 の 1 枚目の画像、level 9）
- `pako.deflate` は `new Deflate` + `push(input, true)` で、`onEnd` がチャンクの並びを新しい 1 つのバッファに平坦化する（`lib/deflate.js:291-296, 334-337`、`utils/common.js:30-48`）。終了時に結果が 2 回分存在する。
- `Deflate` の `onData` を差し替えると、満杯になるたびに新しい 16 KiB バッファが割り当てられる（`lib/deflate.js:225, 252`）ので、チャンクをコピーせずにそのまま保持できる。
- 結果: 入力 52,308,663 B → 一発呼び出し 175,916 B、ストリーミング 175,916 B で**バイト単位で一致**。ストリーミングは 11 チャンクで、すべて別々のバッファ。終了時の保持量は、一発呼び出し 356,140 B（チャンク + 平坦化した結果）に対し、ストリーミング 180,224 B（チャンクのみ）。上限 87,958 B を設定すると、出力 98,304 B（上限 + 16 KiB 以内）で中止した。
- **推奨: Production は `pako.Deflate` + `onData` のストリーミングを使い、チャンクをそのままチャンク writer に渡す。一発呼び出しの `pako.deflate` は使わない。** 研究用の試作（`optimizer.mjs`）は一発呼び出しのままで、圧縮後のバイト列は同じ。

| 構成 | 固定分 | 読み込みの瞬間を含むピーク | P（すべて最悪値で事前判定） | R の算術（参考。対応の主張ではない） |
|---|---:|---:|---|---|
| B1 pdf-lib、元ファイルを保持 | 707.4 MiB | 707.4 MiB | 1,455.7 MiB → 2 GiB | 512: 不可（−195.4 MiB）、1 GiB: 可（余裕 316.6 MiB） |
| **B1 pdf-lib、読み込み後に元ファイルを手放す**（フォールバックは File から読み直し） | 457.9 MiB | **499.2 MiB**（読み込みの瞬間） | 1,206.2 MiB → 2 GiB | 512: 算術上は収まる（余裕 **12.8 MiB**、予約 54.1 MiB）→ **DEFERRED**。**1 GiB: Stage 1 の必須プリセット**（余裕 524.8 MiB、予約 566.1 MiB） |
| B2 自前パーサ（ストリームは元のビュー） | 457.9 MiB | 457.9 MiB | 1,206.2 MiB → 2 GiB | 512: 算術上は余裕 54.1 MiB（後の bounded-memory 段階の候補） |

**Stage 1 の判断（RF-30-01）**
- **方式 R の考え方は推奨**として残す。
- **約 250 MiB を 512 MiB で = 未証明 / DEFERRED**。算術上は元を手放す構成で収まるが、読み込みの瞬間の余裕は 12.8 MiB しかない。さらに、オブジェクトの負担（PER_OBJECT）は合成コーパスでしか測っておらず、ブラウザのヒープ・GC のタイミング・Blob の挙動は測っていない。実行時の上限もまだ設計上の契約にすぎない。
- **Stage 1 では、約 250 MiB の入力には 1 GiB プリセットが必要**（元を手放す構成で、ピーク時の余裕 524.8 MiB、予約枠 566.1 MiB）。512 MiB での対応は、後の bounded-memory 段階（コピーしないパーサ、ブラウザでの計測）に送る。
- 方式 P は、今日の 1 GiB より悪い（2 GiB が必要）。すべての画像が全く縮まない最悪の場合を想定するためで、ユーザー体験としては採れない。
- 方式 R は、圧縮後のサイズという**事前に知り得ない量**を、**実行中の実バイト**で管理する。Processor では、保全系の操作の出力上限がすでに実行時の `checkActualOutput` に置かれており、同じ考え方である。
- 実測（MeasuredOnly、Node）: pako 高速版 + 元ファイルを手放す構成で、f01 の増分 RSS は g1 +100.2 / g2 +93.6 MiB、本番の Optimize は +250.3 / +250.0 MiB。

## 13b. Stage 1 のバッチ境界（RF-30-03）
- 現行の UI は、選んだ全ファイルの `bytes` を実行前に `planned[]` に読み込んで保持する（`PdfTools.tsx:219`、§3）。元のバッファを読み込み後に手放す方式は、他のファイルの元が保持されたままでは何も抑えない。
- **Stage 1 の Optimizer v2（画像対応）は 1 ファイルのみ**。2 ファイル以上を選んで Optimizer v2 を実行しようとした場合は、明示的に拒否する。先頭のファイルだけを黙って処理することはしない。
- 他の Processor ツールのバッチ動作は変えない。
- **バッチ / ZIP の Optimizer v2 は DEFERRED**。対応するには、ファイルを 1 つずつ読み込んで手放す所有権のモデルと ZIP のメモリモデル、そのゲートが別に必要。
- この境界は `model.json` の `stage1.boundary` に記録し、ゲートの `stage1SingleFileOnly` で確認する。

## 14. 出力の安全モデル
**事前判定（決定的）**
- 入力バイト数、ページ・オブジェクト数の上限
- 読み込みの瞬間 = S + Σストリーム + objects × PER_OBJECT（B1）
- 最大画像の処理 = Σ（デコードしたサンプル、R1 の予測器付き本体、最大の R2 形式、最良候補 ≤ 元のストリーム、圧縮中の候補 ≤ 元のストリーム + 16 KiB（実行時の上限）、pako 2.1.0 の状態配列）（§13）。Processor の既存の `deflateUpperBound` / `PAKO_STATE_BYTES` は pako 1.0.11 から導いた値なので使わない
- 予約枠 = 上限 − 固定分 > 0 であること

**実行時ゲート（実バイト）**
- 置き換え後の Σストリーム + これまでの出力 + Blob（= 出力）≤ 予約枠。圧縮中に超えたら中止する
- `checkActualOutput`（≤ 256 MiB、値は据え置き）
- 取消・所有権の確認は、ブロックの境界ごと（Comparator v2 と同じ方法）
- 部分的なファイルは公開しない（チャンクは `finish` まで保持し、中止時は破棄）

**置き換えの規則**
- 候補が元のストリームより小さい場合だけ置き換える。したがって Σ置き換え ≤ Σ元ストリーム ≤ S で、出力 ≤ S + 小さな writer の余分。

**全体の規則**
- 最終的に「元のファイルより意味のある分だけ小さい」場合だけ出力する（§17）。

**§17 補足: 「小さくならなければ元を返す」規則**
- 構造だけの再保存は 0.0〜0.1 % しか減らさず、1,359 B のために書き直したファイルを返すのは、利益がないのにリスクだけがある。

## 19. Build / Reuse / Hybrid 推奨
**Hybrid（B）**。読み込み（pdf-lib）と圧縮（pako）は既存の依存を再利用し、画像の分類・正確な表現変換・チャンク writer・安全ゲートは自前で作る。新しい依存はない。

## 20. 推奨する Production 構成
```
File ─(読む)→ bytes ─ pdf-lib load ─→ object graph
                 └─ 読み込み後に手放す（フォールバック時は File から読み直し）
object graph の画像 XObject を 1 つずつ（逐次・yield・取消確認）:
  census → LEAVE / R1 / R1+R2（+ LOSSY は明示的に選んだ場合のみ）
  decode（Flate + 予測器 / ASCIIHex / 非圧縮）→ 正確な表現の解析 → pako + 予測器
  → 元より小さければ context.assign（共有参照にも効く）→ 実行時の予約枠を確認
チャンク writer（オブジェクトごと、ストリームはビュー、xref は最後）→ finish
→ 全体の規則（§17）→ checkActualOutput → Blob(chunks) → saveAs
```
- 圧縮は `pako.Deflate` + `onData` のストリーミング（一発呼び出しの `pako.deflate` は使わない）。候補ごとに出力バイトを数え、勝てなくなった時点で止める（§13）。
- **Stage 1** = 1 ファイルのみ（2 ファイル以上は明示的に拒否）、B1（pdf-lib のまま、読み込み後に元を手放す）+ 方式 R。**約 250 MiB の入力は 1 GiB プリセットが必要**。512 MiB でのこのサイズの対応は主張しない。
- 後の bounded-memory 段階: B2（コピーしないパーサ）で読み込み時の倍化をなくし、ブラウザでヒープ・GC・Blob を計測してから、512 MiB での約 250 MiB を改めて判断する。バッチ / ZIP の Optimizer v2 も、独自のメモリモデルとゲートを付けてこの段階以降で扱う。

## 22. 依存関係の推奨
**新規依存なし。** pdf-lib 1.17.1 と pako 2.1.0（どちらも既存の直接依存）。AGPL のエンジン（MuPDF、Ghostscript、cpdf）は採らない。pako 2.1.0 は `Deflate` + `onData` のストリーミングで使う。pdf-lib が内部で使う pako 1.0.11 とは別物で、Production の `deflateUpperBound` / `PAKO_STATE_BYTES`（1.0.11 から導いた値）は 2.1.0 の見積りに流用しない。

## 23. UX の推奨（名称は仮）
| モード | 内容 | 既定 |
|---|---|---|
| **無損失（推奨）** | 構造の再保存 + 画像の可逆再圧縮（R1/R2）。画質・解像度は変わらない | ○ |
| **軽量（画質が変わります）** | 上記に加え、スキャン・写真の 8 bit 画像を JPEG 化（品質は選択式）。線画は可逆のほうが小さければ変えない | 明示的に選択 |
| 解像度を下げる | 別の明示的な選択肢。線の再現率が下がる警告付き | 既定にしない |

結果の要約: 元のサイズ、最適化後のサイズ、削減率、最適化した画像数、そのまま残した画像数（理由別）、画質・解像度が変わったかどうか（無損失では「変わっていません」）。

## 24. 未解決事項（Human の判断事項）
1. **メモリの受け入れ方式**: 方式 R（固定分を事前判定 + 圧縮次第の部分を実行中の実バイトで管理し、超えたら中止して何も公開しない）を推奨する。採らなければ、250 MB の可逆最適化は 2 GiB が必要（方式 P）。
2. **Stage 1 の範囲（推奨）**: 1 ファイルのみ（2 ファイル以上は明示的に拒否）。約 250 MiB の入力は 1 GiB プリセットが必要。512 MiB でのこのサイズの対応と、バッチ / ZIP の Optimizer v2 は DEFERRED。
2b. Stage 1 で、約 250 MiB より小さい入力をどのプリセットで受け入れるか（受け入れ式と、読み込みの瞬間に求める余裕）は、実装段階で明示的な余裕付きで決める。
3. 「小さくならなければ元を返す」規則の閾値（1 % など）。
4. 軽量（非可逆）モードを段階 1 に含めるか。含める場合、JPEG の品質と、スキャンと写真の判定方法（色数・グレーかどうか・線の割合など）。
5. Acrobat の実ファイルの解析（ツールは用意済み）。
6. 実ファイルに多い構造（JBIG2 / CCITT、インライン画像、OCG、増分更新、オブジェクトストリームの多い PDF）の検証範囲。チャンク writer は今のところオブジェクトストリームを作らないので、オブジェクト数の多い元ファイルは書き直しで大きくなり得る（全体の規則で元を返す）。
