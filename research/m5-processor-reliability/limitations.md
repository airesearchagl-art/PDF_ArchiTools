# Limitations and unverified items

## Of the evidence

- **Synthetic corpus only.** Every document is generated by pdf-lib. Real CAD
  and scanner output uses ICC colour spaces, shadings, patterns, Type3 fonts,
  soft masks, JBIG2/CCITT/JPX and 1-bit images far more than this corpus does.
  The candidates' refusal rate on real drawings is **unmeasured**; that is the
  first thing a follow-up spike must measure.
- **The signature is a structural proxy.** `/ByteRange` covers the file and
  `/Contents` holds a SHA-256 of it; there is no certificate and no PKCS#7.
  "Invalidated" means the signed bytes are no longer the file — the first thing
  a real verifier checks, not the whole of what it checks.
- **Browser heap is not measured.** Raster peaks are computed from the code
  (canvas, readback, JPEG, data URL, retained JPEG); PDF.js' worker memory and
  Chrome's canvas internals are not included. A0 @300 dpi Monochrome was
  deliberately not run (≈ 1 GiB of RGBA per page).
- **The canvas limit is measured on one machine** (headless Chrome, Windows):
  139 Mpx allocated, 279 Mpx did not. Other browsers, GPUs and memory states
  differ; a preflight must measure, not assume, the limit.
- **Page order for rasterised outputs is read from pixels** (their text is
  gone), using a fixture whose pages differ visibly; it proves order, not
  content.
- **Annotation appearances in rasterised output** are removed as objects
  (measured). Whether PDF.js drew their appearance into the raster is inferred
  from its default `annotationMode`, not measured.
- **Visual numbers decide nothing.** They are reported beside structural
  verdicts; a 240-px thumbnail difference is evidence of placement, not of
  preservation.

## Of the prototypes

- **Monochrome B/C** convert Device RGB/CMYK/Gray colour operators, Form
  XObjects and annotation appearances, and Flate/DCT 8-bit DeviceRGB/Gray
  images; everything else is refused. Not handled: ICCBased/CalRGB/Lab
  (refused, although often convertible), Indexed images, 1-bit images that are
  already monochrome (refused; could pass through), JPX/JBIG2/CCITT, inline
  images, shadings and patterns, Type3 glyph colour, soft-mask groups, colour
  in `/DA` beyond simple operators. Widgets whose appearance a viewer
  regenerates are covered only through `/DA`, `/MK` and `/C`.
- **Margin in-place** moves `/Rect`, `QuadPoints`, `Vertices`, `L`, `CL`,
  `InkList` and scales `/RD`; it does not rewrite explicit destinations
  (`/Dest [page /XYZ x y z]`) in links or outlines, nor widget font sizes
  (appearances scale with the /Rect, regenerated ones may not).
- **Optimize O3** resamples to a full-page upper bound, not to each image's
  placed size, so it keeps more pixels than strictly needed; it re-encodes as
  JPEG (lossy) and skips images with a soft mask.
- **The job prototype** discards a superseded file at the next boundary; the
  existing per-file functions cannot be interrupted mid-file.
- **Every candidate still re-serialises.** None keeps a signature valid;
  pdf-lib has no incremental save.

## Unverified

- ZIP generation failing (`zip.generateAsync` is outside the per-file try and
  `setIsProcessing(false)` is not in a `finally`, `PdfTools.tsx:159-164`):
  inferred to leave the UI stuck in 処理中, not exercised.
- Contrast and margin-setting changes mid-run: same closure as DPI, not
  separately exercised.
- Encrypted input to the five operations: not in the corpus (pdf-lib cannot
  write encryption); `assessSource` refuses it by its own tests.
- Real-world file sizes for O1/O3 on dense scans; JPEG sizes here are small
  because the drawings are mostly paper.

## Of the scope

- No production code changed; the defects in `baseline.md` stand on `main`.
- The hardened lanes were not redesigned; their signature and metadata
  behaviour is recorded as compatibility notes only.
