# Limitations and unverified items

## Of the evidence

- **Local research gate, not Core CI.** Every number here comes from
  `scripts/research-gate.mjs` run locally on this branch and committed as
  `evidence.json`. Core CI at the exact head runs the existing backbone only;
  it does not run this gate.
- **Synthetic corpus only.** Every document is generated by pdf-lib. Real CAD
  and scanner output uses ICC colour spaces, shadings, patterns, Type3 fonts,
  soft masks, JBIG2/CCITT/JPX and 1-bit images far more than this corpus does.
  The candidates' refusal rate on real drawings is **unmeasured**.
- **The signature is a structural proxy.** `/ByteRange` covers the file and
  `/Contents` holds a SHA-256 of it; there is no certificate and no PKCS#7.
- **Browser heap is not measured.** The Raster Budget is a source-derived model
  whose exact terms (canvas, data URL) and bounds (JPEG, outputs) are validated
  against production on 16 pages; its conservative and inferred terms (PDF.js
  scratch canvases, source-image decode, pdf-lib and JSZip buffers) are not
  measured in the heap.
- **The JPEG bound comes from one encoder.** 0.783 B/px worst case on this
  Chrome's JPEG encoder at q0.8, bounded at 1.0 B/px; other browsers' encoders
  are unmeasured. The gate fails its apparatus if the measured worst case ever
  exceeds the bound.
- **The canvas limit is measured on one machine** (139 Mpx allocated, 279 Mpx
  did not). The recommended 128 Mi px ceiling is a policy below that, paired
  with a runtime allocation probe; the portable limit of every supported
  browser is not established here.
- **Page order for rasterised outputs is read from pixels** (their text is
  gone), on a fixture whose pages differ visibly.
- **Annotation appearances in rasterised output** are removed as objects
  (measured); whether PDF.js drew them into the raster is inferred from its
  default `annotationMode`, not measured.
- **Visual numbers decide nothing.** Structural verdicts decide; thumbnails
  measure placement.

## Of the prototypes

- **Source facts** read at the dictionary level; a document with a broken but
  loadable AcroForm reads as `formInspectionState: 'unreadable'`, which every
  H7 candidate treats as a possible signature.
- **Monochrome B/C** convert Device RGB/CMYK/Gray colour operators, Form
  XObjects and annotation appearances, and Flate/DCT 8-bit DeviceRGB/Gray
  images; everything else is refused (ICCBased/CalRGB/Lab, Indexed, 1- and
  16-bit images — 1-bit could pass through — JPX/JBIG2/CCITT, inline images,
  shadings, patterns, Type3 glyph colour, soft-mask groups).
- **Margin in-place** carries annotation geometry, internal destinations of the
  eight standard types (links, GoTo actions and `/Next` chains, outlines,
  `/Dests`, the `/Names /Dests` tree) and widget `/DA`/border; it refuses
  structure destinations, `/GoToE`, unknown destination types, destinations
  into no page, annotations not wholly visible, unknown annotation types and
  underflowing content. Left unchanged by design: `/GoToR` (another file's
  coordinates). Not covered: JavaScript actions that compute coordinates;
  widget appearances that depend on font metrics other than `/DA` size.
- **Optimize O3** sizes each image from the CTM at every `Do`; it does not
  account for clipping that shows only part of an image (keeping more pixels
  than needed — conservative), treats annotation-drawn images, images used as
  soft masks and images never drawn as uncertain (never downsampled), and
  re-encodes as JPEG (lossy) only when smaller.
- **The job prototype** runs files sequentially; B3's "independent" is per-file
  ownership and publication, not parallel execution. A superseded file finishes
  computing and is discarded at the next boundary: the existing per-file
  functions cannot be interrupted mid-file.
- **The overlay-as-annotation** candidate for H13b was measured in PDF.js'
  canvas rendering only; editors and PDF.js' interactive form layer treat
  annotations differently.
- **Every candidate still re-serialises.** None keeps a signature valid;
  pdf-lib has no incremental save.

## Unverified

- ZIP generation failing (`zip.generateAsync` is outside the per-file try and
  `setIsProcessing(false)` is not in a `finally`, `PdfTools.tsx:159-164`):
  inferred to leave the UI stuck in 処理中, not exercised.
- Contrast and margin-setting changes mid-run: same closure as DPI, not
  separately exercised.
- Encrypted input: not in the corpus (pdf-lib cannot write encryption); the
  facts reader reports `encrypted` from pdf-lib's own detection.
- Real-world sizes for O1/O3 on dense colour scans.

## Of the scope

- No production code changed; the defects in `baseline.md` stand on `main`.
- The hardened lanes were not redesigned; their signature and metadata
  behaviour is recorded as compatibility notes only.
