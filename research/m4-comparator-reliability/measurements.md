# M4 measurements

Produced by `scripts/m4-comparator-research-gate.mjs` against `main` at
`44cb82db7365e436c642f375852f22990c45a6ce`. The machine-readable form is
`evidence.json`. Everything here is **Observed**; proposals live in
`architecture.md` and verdicts in `decision-matrix.md`.

The compositing measured is the **production** `src/utils/pdfDiff.ts`, driven in
a real browser. Measuring a rewrite of it would say nothing about what ships.

## 0. The corpus

42 synthetic drawings, generated by `scripts/m4-comparator-fixtures.mjs` and not
committed. The same plan — border, title block, repeating grid, a labelled title
— drawn as a fraction of whatever sheet it is given, so "the same drawing on A1
and A3" means the same picture at two physical scales.

Asserted distinct before anything is compared, because a corpus that does not
actually differ makes every number below meaningless:

| | |
| --- | --- |
| the four rotations | identical content — **89 path operators on all four** |
| the crop pair | **both 495x741 displayed**, origins (0,0) and (50,70) |
| the crop-and-rotate trio | the same CropBox at (50,70), at `/Rotate` 90, 180 and 270 |
| the sheets | A4 595 < A3 842 < A1 1684 points wide |
| the page-count pair | 3 pages against 2 |
| the blank-third fixture | 3 pages, the third empty |
| the small-change family | one sheet at one size at `/Rotate 0`, seven variants |

The small-change family has its own base sheet rather than extending `base-a4`,
so that adding it leaves every number already measured against `base-a4`
untouched. Whether each of its variants is really a change is settled by the
pixels in §4f, not by an operator count — `1200` and `1300` draw the same number
of operators.

## 2b. Every accepted mapping is rigid

Candidate B maps other members onto slot 1. The previous prototype computed that
mapping from the pages' **display** dimensions, which carry `/Rotate`. For an A4
at `/Rotate 0` against the same A4 at `/Rotate 90` that produces `x = 0.707`,
`y = 1.414`, `uniform: false`, `rigid: false` — and the plan returned
`READY_TO_COMPARE` anyway, offering to compare a drawing squashed in one axis
and stretched in the other, on two pages that are the same piece of paper.

The mapping is now taken in canonical upright space, where a quarter turn has
already been removed by the renderer. Both numbers are recorded, the rejected
one beside the one that replaced it:

| pair | plan | mapping applied | the display-plane mapping would have been | compared |
| --- | --- | --- | --- | --- |
| `/Rotate 0` vs `0` | `READY_TO_COMPARE` | identity, rotation 0 | 1.000 / 1.000 | **MATCH**, 0 px |
| `/Rotate 0` vs `90` | `READY_TO_COMPARE` | identity, rotation 0 | **0.707 / 1.414** | **MATCH**, 0 px |
| `/Rotate 0` vs `180` | `READY_TO_COMPARE` | identity, rotation 0 | 1.000 / 1.000 | **MATCH**, 0 px |
| `/Rotate 0` vs `270` | `READY_TO_COMPARE` | identity, rotation 0 | **0.707 / 1.414** | **MATCH**, 0 px |
| crop origin only | `READY_TO_COMPARE` | identity, rotation 0 | 1.000 / 1.000 | **MATCH**, 0 px |
| crop origin + `/Rotate 90` | `READY_TO_COMPARE` | identity, rotation 0 | **0.668 / 1.497** | **MATCH**, 0 px |
| crop origin + `/Rotate 180` | `READY_TO_COMPARE` | identity, rotation 0 | 1.000 / 1.000 | **MATCH**, 0 px |
| crop origin + `/Rotate 270` | `READY_TO_COMPARE` | identity, rotation 0 | **0.668 / 1.497** | **MATCH**, 0 px |
| a different physical sheet | **`GEOMETRY_MISMATCH`** | none | 0.707 / 0.707 | not compared |

The invariant, asserted by the gate over every accepted plan:

```
status == READY_TO_COMPARE  =>  every mapping.rigid == true
                            and every |scaleX - scaleY| == 0
                            and every renderRotation == 0
```

It holds by construction rather than by check: there are two cases and no third
— the same sheet within 1 pt, mapped by the identity, or a different sheet,
refused. The sub-point disagreement the tolerance permits is reported as a
residual in points, not folded into a scale factor.

## 4b. A plan, then a verdict

The first version of this prototype returned `CHANGE` as soon as a comparison
was eligible, so `CHANGE` was doing two jobs and an identical drawing came back
as one. A plan says whether the comparison can be made; only a comparison that
actually ran may say MATCH or CHANGE.

| | plan | verdict | differing pixels |
| --- | --- | --- | --- |
| identical | `READY_TO_COMPARE` | **MATCH** | 0 |
| a wall added | `READY_TO_COMPARE` | **CHANGE** | 8530 (9.6%) |
| rotation only | `READY_TO_COMPARE` | **MATCH** | 0 |
| crop origin only | `READY_TO_COMPARE` | **MATCH** | 0 |
| a different sheet | `GEOMETRY_MISMATCH` | **none** | not compared |
| a different sheet, human alignment supplied | `UNSUPPORTED` | **none** | not compared |

Match tolerance **0**. The previous round set it at 0.5% of ink on the reasoning
that rendering is not bit-exact; §4f shows that reasoning does not hold on this
corpus and that the floor hid real changes.

The rotation and crop rows reach MATCH only because the plan renders upright;
that is what "the plan is ready" means for those pairs.

The last row changed from the previous round, deliberately. Supplying
`{ x, y, rotation, scale }` used to return `READY_TO_COMPARE`; it now returns
`UNSUPPORTED` with `requires: alignment-architecture-sub-spike`, because the
prototype records that object without defining what it means — no coordinate
space, no units, no transform order, no pivot, no bounds, and no aligned
comparison ever run. The alignment is kept on the result as `recordedAlignment`
with `appliedAlignment: null`. Same rule as §4e: a plan may not claim a
comparison it has no contract for.

## 4c. More than two members

The shipped rule marks a pixel matched when **any other layer** has ink near it.
With two members that is the same as agreement. With four it is not.

| | any-other-layer (shipped) | reference-pairs |
| --- | --- | --- |
| four identical | 0.0% **MATCH** | MATCH |
| three the same, one changed | 9.6% **CHANGE** | CHANGE |
| **two against two** | **0.0% MATCH** | **CHANGE** |
| **reference and three different** | **0.0% MATCH** | **CHANGE** |

The last two rows are the finding. In *two against two*, A and B put a wall in
one place and C and D put it in another; every pixel finds a partner and the
comparison comes back **perfectly clean**. In *reference and three different*,
three documents each differ from the reference and from each other, and it is
still reported as a match.

Comparing each non-reference member against slot 1 catches both: the two-against-
two pairs measure `identical-a4: 0.0%`, `wall-at-y-a4: 19.3%`,
`wall-at-y-a4-copy: 19.3%`, and the overall verdict is MATCH only when every
pair matches.

| plan | members | contract | status |
| --- | --- | --- | --- |
| two members | 2 | two-only or reference-pairs | `READY_TO_COMPARE` |
| four members | 4 | two-only | `UNSUPPORTED` |
| four members | 4 | reference-pairs | `READY_TO_COMPARE`, 3 pairs |
| one member | 1 | any | `UNSUPPORTED` |
| two members | 2 | **consensus** | **`UNSUPPORTED`, deferred** |
| four members | 4 | **consensus** | **`UNSUPPORTED`, deferred** |

All-member consensus is described in `architecture.md` and implemented nowhere,
so it is refused at every member count rather than returned as a plan. Nothing
has been run under it against a blank member, a member the other documents do
not have, or a member that failed to render — the cases where a stricter rule
diverges most from its own description. The implemented contracts are the two
that were measured, and the gate asserts that there are exactly two of them.

## 4f. Changes small enough for a ratio floor to swallow

Every pair here except the control is a **true** change to the drawing, and the
family has its own base sheet so that adding it changes none of the numbers
measured against `base-a4`. `canonical` is the verdict with no floor;
`0.5% floor` is what the previous round's tolerance would have said about the
same measurement.

| | pixels | of the ink | canonical | 0.5% floor |
| --- | --- | --- | --- | --- |
| *nothing changed (control)* | *0* | *0.000%* | *MATCH* | *MATCH* |
| a light hatch added | 43 | 0.053% | **CHANGE** | MATCH |
| the pale-hatch fixture | 43 | 0.054% | **CHANGE** | MATCH |
| one digit of a dimension, 1200 → 1300 | 51 | 0.063% | **CHANGE** | MATCH |
| a 4 mm revision triangle added | 160 | 0.198% | **CHANGE** | MATCH |
| one short fine line added | 200 | 0.248% | **CHANGE** | MATCH |
| a symbol swapped, circle → square | 394 | 0.488% | **CHANGE** | MATCH |
| a wall added, for scale | 8530 | 9.640% | **CHANGE** | CHANGE |

**Six of seven true changes were reachable only without the floor.** The floor
was justified on the grounds that a zero floor would make MATCH unreachable; the
control row is the answer to that — a redraw of the same sheet differs by 0
pixels, as do the identical, rotation-only and crop-origin controls elsewhere in
this document.

The alternative to a ratio floor is the physical tolerance applied to the mask,
and it is measured on the same pairs rather than assumed to be free. Changed
pixels, swept finely enough to find where a real change stops being visible:

The sweep is run at **every resolution the shipped Comparator offers** —
`PdfComparator.tsx:805-808` gives 72, 150, 300 and 450 DPI. Changed pixels for
the dimension string, and the largest tolerance at which the change is still
reported:

| dpi | 0 | 0.05 | 0.1 | 0.15 | 0.2 | 0.25 | 0.3 | 0.4 | 0.5 mm | safe to |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **72** | 10 | 10 | 10 | 10 | **0** | **0** | **0** | **0** | **0** | **0.15 mm** |
| 150 | 51 | 51 | 14 | 14 | 14 | 14 | **0** | **0** | **0** | 0.25 mm |
| 300 | 186 | 96 | 96 | 49 | 49 | 18 | 1 | **0** | **0** | 0.3 mm |
| 450 | 401 | 248 | 166 | 113 | 73 | 73 | 38 | **0** | **0** | 0.3 mm |

The whole-pixel rounding behind it:

| dpi | 0.05 | 0.1 | 0.15 | 0.2 | 0.25 | 0.3 | 0.4 | 0.5 mm |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 72 | 0 | 0 | 0 | 1 | 1 | 1 | 1 | 1 |
| 150 | 0 | 1 | 1 | 1 | 1 | 2 | 2 | 3 |
| 300 | 1 | 1 | 2 | 2 | 3 | 4 | 5 | 6 |
| 450 | 1 | 2 | 3 | 4 | 4 | 5 | 7 | 9 |

And the same sweep on a swapped symbol — a circle changed to a square — at
72 dpi: 112 differing pixels at 0 mm, **32** from 0.2 mm on. The setting does
not only move marks around; it erases shape changes too.

Four things follow, and all four belong in the H6 policy rather than in a
footnote:

- The control needs no tolerance **at any setting or any resolution** — a redraw
  of the same sheet differs by 0 pixels throughout. The tolerance is not there
  to absorb render variance; there is none to absorb.
- **72 dpi is the weakest**, at 0.15 mm, and it would have been missed by
  sweeping the middle of the range. A millimetre is fewer pixels there *and* the
  mark is smaller, so the digit is gone by 0.2 mm while 150 dpi still sees it.
- The setting does not erode changes evenly. A 4 mm revision triangle survives
  the whole range at 150 dpi; the digit and the symbol do not. It erodes the
  small ones, which are the ones hardest to catch by eye.
- The same millimetres are not the same radius at every resolution. Below about
  0.1 mm the setting is finer than the render at 72 and 150 dpi.

That trade belongs to the user in millimetres, under a stated policy — not to a
share of the page chosen by a developer, and not to a unit with no bounds. The
maximum is the **minimum** safe bound across the four, **0.15 mm**.

## 4g. The same comparison, painted three ways

The verdict is computed from the ink masks before anything is painted. The
composite ratio is what the earlier rounds counted — pixels in the painted
result that are neither white nor grey — and it is a property of the palette.

| | verdict | mask | composite change pixels |
| --- | --- | --- | --- |
| **a changed pair** — blue/red, black match, opaque | CHANGE | 51 px | 51 |
| **a changed pair** — grey/grey, grey match, 0.2 opacity | CHANGE | 51 px | **0** |
| **a changed pair** — green/magenta, white match | CHANGE | 51 px | 51 |
| **an identical pair** — all three palettes | MATCH | 0 px | 0 |

The middle row is the one that matters: give both layers the same grey and the
composite-derived count falls to zero on a drawing that genuinely changed. The
mask does not move, and neither does the verdict.

## 8. What counts as ink

(`pdfDiff.ts:57-60`). `detectChangeBounds` uses **any** channel

| black | 0,0,0 | ink | ink |

## 9b. The threshold when nothing matches

Two sheets with no shared border, title block or grid, so almost no ink matches

| **not matching**, A4 300 dpi | 6 | 2480x3507 | 1.7% | **100.0%** | 217 ms |

## 10a. The working set of the proposed architecture

Section 10 measures the **shipped** pipeline, which hands every layer's RGBA to
the compositor at once. The proposed pipeline does not, so it needs its own
model — and the previous round's "within 512 MiB" claim was taken against the
wrong one.

### The picture is a function of the masks

The shipped compositor starts each pixel white and multiplies in a *flat* colour
wherever the ink predicate is true; it never reads the source pixel's intensity.
So the composite can be painted from the ink masks and the dilated masks alone.
Asserted rather than argued:

| | members | radius | match opacity | bytes compared | differing |
| --- | --- | --- | --- | --- | --- |
| two members, exact | 2 | 0 | 1 | 8,706,856 | **0** |
| two members, 0.5 mm | 2 | 3 | 1 | 8,706,856 | **0** |
| two members, faint match colour | 2 | 0 | 0.25 | 8,706,856 | **0** |
| four members, 0.25 mm | 4 | 1 | 1 | 8,706,856 | **0** |

**34.8 MB of output, byte-identical.** The consequence is the whole memory
model: no member's RGBA survives the phase that extracted its mask.

### The encoder the bound belongs to

Two earlier versions of this got the allowance wrong in two different ways.
First 0.15 B/px from four measured composites — a compression ratio, which a
fail-closed gate may not rest on. Then PNG's stored-block worst case applied to
`canvas.toBlob`, which is a real formula about an encoder **this architecture
does not control**: the browser picks its own DEFLATE strategy, block layout,
IDAT chunking and internal scratch.

So the encoder is owned, with a stated contract — RGBA8, filter 0, DEFLATE
stored blocks of 65,535 bytes, IDAT chunks of 1 MiB — and the size is exact
rather than bounded:

| | written | predicted | round trip | B/px | browser PNG |
| --- | --- | --- | --- | --- | --- |
| A4 150 dpi, changed | 8,709,434 | 8,709,434 | **lossless** | 4.001 | 0.031 |
| A4 150 dpi, dense | 8,709,434 | 8,709,434 | **lossless** | 4.001 | 0.032 |
| A3 150 dpi, matched | 17,410,762 | 17,410,762 | **lossless** | 4.001 | 0.029 |

"Round trip" is the browser decoding the bytes back and every pixel compared:
0 differing bytes. Scratch is one row — 4,965 bytes on a 1,241 px sheet —
because the encoder streams filter byte and row bytes straight into the stored
block rather than building a filtered raster and a zlib buffer first.

**The price is the file size**, and it is the trade being proposed: stored
blocks do not compress, so 4.001 B/px against the browser's 0.031. That goes to
**H5** rather than being inherited. JPEG has no comparable provable worst case,
which is a further reason to prefer PNG.

The browser measurements below stay as **performance** evidence only:

| | pixels | JPEG | PNG |
| --- | --- | --- | --- |
| A4 150 dpi, changed | 2.2 Mpx | 0.036 B/px | 0.031 B/px |
| A4 300 dpi, changed | 8.7 Mpx | 0.025 B/px | 0.028 B/px |
| A4 150 dpi, dense | 2.2 Mpx | **0.050 B/px** | 0.032 B/px |
| A3 150 dpi, matched | 4.4 Mpx | 0.027 B/px | 0.029 B/px |

What a browser emits says nothing about what it allocates while emitting it.
A data URL of the same bytes costs 4/3 at two bytes a character: 394 MB against
278 MB for an A3 at 300 dpi, which is why the budget is taken on handing back a
`Blob` over the encoded bytes.

### The peak, phase by phase

`peakWorkingSet = max over phases`, not a sum. Members are rendered serially;
under reference-pairs the pairs are processed serially with the reference mask
and its dilation computed once and reused.

A3 at 300 dpi, two members, 0.5 mm — 17.4 Mpx:

| phase | live |
| --- | --- |
| render | 157 MB |
| mask extraction | 104 MB |
| dilation | 87 MB |
| comparison | 87 MB |
| **presentation** | **278 MB** |

| at 0.5 mm, two members unless stated | B/px | peak | |
| --- | --- | --- | --- |
| A4 300 dpi, 0 mm | 14 | 122 MB | within |
| A4 300 dpi | 16 | 139 MB | within |
| A3 300 dpi | 16 | **278 MB** | within |
| A2 300 dpi | 16 | **557 MB** | **refused** |
| A1 300 dpi | 16 | 1115 MB | **refused** |
| A1 300 dpi, four members | 18 | 1255 MB | **refused** |

Two rows moved when the compression assumption came out. A3 is 278 MB rather
than 211 MB, still within but on a derived margin. **A2 at 300 dpi is now
refused at 557 MB** where the ratio-based model called it 423 MB — a comparison
a user can ask for, admitted by an allowance that happened to fit the fixtures.

For contrast, the shipped model puts A3 at 487 MB — inside the 537 MB ceiling,
counting the wrong buffers; adding the four mask buffers to *that* figure would
have given about 557 MB and refused it. Neither number described the
architecture that was chosen.

Keeping `toDataURL` instead of `toBlob` would put A3 at **464 MB**.

A tolerance of zero allocates no dilation buffers: 14 B/px against 16. Four
members cost 18 B/px rather than 20, because the pairwise presentation (§4h)
holds two dilations at a time rather than one per member.

## 10b. The work budget

A second ceiling, and a separate one: an A4 at 300 dpi with two members is
139 MB of working set under the phase model — comfortable — and 69,578,880
comparison-work units under the selected algorithm.

A work unit is one pixel read. Per compared group:

```
    pixels x sourceMembers                                    every pixel, once
  + pixels x sourceMembers x comparedOtherMembers x (2r+1)²     the neighbourhood
```

summed over the groups the contract produces. Proposed ceiling:
**`MAX_COMPARISON_WORK_UNITS = 12,000,000,000`** — a recommendation requiring
human approval, not a measured threshold.

| at 0.5 mm, two members unless stated | box | groups | work units | |
| --- | --- | --- | --- | --- |
| A4 300 dpi, radius 0 | 1 | 1 | 34,789,440 | within |
| A4 300 dpi, radius 1 | 9 | 1 | 173,947,200 | within |
| A4 300 dpi, radius 2 | 25 | 1 | 452,262,720 | within |
| A4 300 dpi | 169 | 1 | 2,957,102,400 | within |
| A3 300 dpi | 169 | 1 | 5,917,083,920 | within |
| A4 300 dpi, four members, reference-pairs | 169 | 3 | 8,871,307,200 | within |
| A1 300 dpi | 169 | 1 | 23,694,575,520 | **refused** |
| A0 600 dpi | 625 | 1 | 698,586,380,184 | **refused** |

The previous shape, `pixels x radius² x members`, was described as an upper
bound and is not one: the radius-0 row above is **34,789,440 units** where that
formula gives **zero**, and a radius-0 comparison still reads every pixel of
every member. It also omitted the contract, so the four-member row would have
costed the same as the two-member one instead of three times as much.

Calibration lives below, against the algorithm the planner is bound to — a unit
is not a fixed amount of work, so a figure taken against the shipped scan would
describe an algorithm this design does not use.

The bound belongs to the algorithm, not to the feature. The same A1 at the same
tolerance is 23,694,575,520 units under the shipped nested scan and
**557,519,424** under a separable dilation — refused under one and comfortably
within the ceiling under the other.

Refusals are typed and named, never quieter comparisons:

| | |
| --- | --- |
| over the ceiling | `OVER_WORK_BUDGET`, quoting units against ceiling |
| a contract with no derived bound (consensus) | `OVER_WORK_BUDGET`, "no work bound is derived for this contract" |
| arithmetic outside the safe-integer range | `OVER_WORK_BUDGET`, "not representable" |
| fewer than two members | `OVER_WORK_BUDGET` before any estimate is attempted |

Every estimate records its requested and effective settings together, and
`degraded` is false on all of them, so a silent downgrade could not pass
unremarked.

### What a unit costs, under the algorithm that ships

A unit is not a fixed amount of work. The same A1 at the same tolerance:

| | work units |
| --- | --- |
| the shipped nested scan | 23,694,575,520 |
| the separable dilation | **557,519,424** |

Forty-two times fewer, for identical physical work. So the ceiling means nothing
until the algorithm is named, and `estimateComparisonWork` now has **no

### Storage capacity is a third budget

`totalEncodedBytes` is known before rendering, so it is a preflight like the
others. What it compares against is advisory, so there are three outcomes:

| | required | no readable quota | 2 GB quota | 1 TB quota |
| --- | --- | --- | --- | --- |
| 5 pages, 4 members, spooled | 0.52 GB | **unknown** | within | within |
| 200 pages, 4 members, spooled | **20.88 GB** | **unknown** | **insufficient** | within |

An earlier round reported the 20.9 GB row as "within" because the *RAM* peak was
4 MiB. That was true and it was not the whole sentence. `unknown` is now a
distinct outcome from `within`: a quota that cannot be read is not room. Half
the reported free space is the headroom, because the quota is shared with
everything else the origin has stored.

This browser reported a 1.2 TB quota at 0 MB usage, which is why the fixed
2 GB and 1 TB comparisons above are in the table rather than the live figure.

### The ceiling is on the job, not the page

Memory is a peak and pages are serial, so the page model above is right for it.
Work accumulates, and the export and the change report both run over ranges:

Costed under the selected algorithm:

| job | pages | work units | |
| --- | --- | --- | --- |
| one A4 page at 300 dpi, 0.5 mm | 1 | 69,578,880 | within |
| three of them | 3 | 208,736,640 | within |
| **173 of them** | 173 | **12,037,146,240** | **refused** |
| one sheet large enough on its own | 1 | 12,627,783,200 | **refused** |
| four members, reference-pairs, three pages | 3 | 626,209,920 | within |
| an export of two pages of a longer document | 2 | 139,157,760 | within |

The third row is the gap a per-page ceiling leaves open: every one of those 173
pages is 69.6e6 units, well inside a 12e9 ceiling, and together they are over
it. The refusal says so — *"173 pages total 12,037,146,240 work units, over a
ceiling of 12,000,000,000; no single page is"* — rather than naming a page that
is not at fault. The page count is derived from the ceiling rather than
hard-coded, so it stays this case if the ceiling is recalibrated.

Pages that cannot be compared stay in the plan at zero work with the reason
recorded (`MISSING_PAGE`, `RENDER_FAILED`), so a job of three pages where two
are uncomparable reports one comparable page rather than quietly costing one.
Reference-pairs are costed on every requested page, not once. An export range
costs only the pages it asked for.

## 10c. Stopping a comparison that has started

The shipped composite is a synchronous nested loop with no yield point, so a
cancellation cannot be observed: by the time it returns, the answer it was asked
to stop producing has been produced. Two replacements, both measured on the
dense non-matching pair at 150 dpi, 1241×1754, 0.9% ink:

| tolerance | box | nested scan | separable dilation | same mask |
| --- | --- | --- | --- | --- |
| 0 mm | 1 | 7 ms | 4 ms | yes |
| 0.25 mm | 9 | 5 ms | 25 ms | yes |
| 0.5 mm | 49 | 4 ms | 23 ms | yes |

**On a sparse drawing the nested scan is the faster of the two**, because it
exits on the first ink it finds. That is a property of the drawing, not of the
algorithm, and it is why a ceiling cannot be derived from it. On the case a
bound has to cover — ink everywhere, matching nothing — the picture inverts:

| tolerance | box | nested scan | separable dilation | same mask |
| --- | --- | --- | --- | --- |
| 0.25 mm | 9 | 25 ms | 28 ms | yes |
| 0.5 mm | 49 | **65 ms** | **28 ms** | yes |

The dilation is flat in the radius; the scan is not. And it is exact rather than
approximate — the change masks are identical in every row of both tables, which
is what makes it a substitution rather than a different comparison.

Banded execution, on the same pair at 0.5 mm, 512-row bands:

| | | |
| --- | --- | --- |
| uncancelled, banded, asynchronous | `READY_TO_COMPARE` in **18 bands** | 41,116 change pixels — the same as the direct computation |
| **synchronous driver**, cancellation scheduled from a timer | ran to completion in **23 ms** | the timer never fired; the cancellation was **never observed** and a verdict was produced |
| **asynchronous driver**, the same cancellation | `CANCELLED` at **band 4 of 18**, 26 ms | `publishable: false`, `result: null` |
| superseded by a newer generation mid-flight | `CANCELLED` | `publishable: false`, `result: null` |

The second row is the point of the section. Bands give a cancellation somewhere
to be *noticed*; they do not give it a way to *arrive*. A driver that never
returns to the event loop leaves the timer — or the click, or the `postMessage`
— in a queue until the comparison has already finished and published.

The yield is `setTimeout(…, 0)` rather than a microtask, deliberately: a
microtask drains before the task queue is touched, so awaiting one would prove
nothing. Timers are one task source served in order, so a cancellation scheduled
before the yield has certainly run by the time it resolves.

A cancelled comparison returns `CANCELLED` and nothing else. Half a change mask
is not a smaller change; it is a different drawing.

What this does **not** establish: nothing here ran inside a Web Worker over
`postMessage`, and no real UI supersession — an unmount, a document swap, a
threshold moved — was exercised. Those belong to the production implementation
gate.

## 13. The gate

`scripts/m4-comparator-research-gate.mjs` re-asserts **229 claims, 92 of them
negative probes**. Several are unusual: the shipped comparator is asserted to
report changes on drawings that are identical. Those are the findings, and a gate
in which the baseline passed everything would prove nothing about why this spike
exists.

It gates the write-up, not the app, and it is **not** wired into Core CI: it
needs a browser, a corpus that is generated rather than committed, and about a
minute to run.
